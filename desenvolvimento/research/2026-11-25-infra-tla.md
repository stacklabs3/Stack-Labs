# Infra do TLA+: requisitos, tempo de checagem, custo de tokens e lugar no pre-push

Pesquisa de 2026-11-25, ticket #72 do mapa #69. A pergunta: quanto custa rodar TLA+ num projeto da
casa? Ela se divide em quatro partes. Primeiro, o que o TLC, o Apalache e o Quint exigem e como
entram na máquina do dev (macOS) e no CI local (ADR 0015 e 0021). Segundo, quanto tempo leva a
checagem de um modelo pequeno e onde ela explode. Terceiro, quantos tokens um agente gasta para
escrever e manter o modelo (ADR 0017). Quarto, se a checagem cabe no pre-push.

Legenda: **[medido]** = número tirado nesta máquina com o modelo e os comandos da seção 6;
**[fonte]** = dito pela fonte primária citada; **[inferido]** = conclusão minha a partir das duas,
sem medição direta.

Máquina da medição: Apple M5, 10 núcleos, 24 GB de RAM, macOS 26.7.1, OpenJDK 25.0.3 (Homebrew),
Node 26.13.0.

## Resultado

| Requisitos do Apalache | Java 21 ou mais novo (25 recomendado), pacote de 192 MB, Z3 embutido, pelo menos 4 GB de RAM recomendados | [fonte] docs do Apalache; [fonte] release v0.63.0 |

## 1. Requisitos e instalação

### TLC (tla2tools)

- **[fonte]** O README do `tlaplus/tlaplus` diz: "The TLA⁺ tools require Java 11+ to run." O
  `tla2tools.jar` vem nas releases do GitHub e `java -jar tla2tools.jar` chama o `tlc2.TLC`
  ([README](https://github.com/tlaplus/tlaplus/blob/master/README.md)).
- **[fonte]** Versões publicadas em 2026-11-25 (`gh release list -R tlaplus/tlaplus`):
  - **v1.7.4** ("Xenophanes"): marcada como *Latest*, de 2024-08-05, jar de 2.274.532 bytes.
  - **v1.8.0** ("Clarke"): ainda marcada como *Pre-release*, jar de 4.511.244 bytes, gerado em
    2026-11-26T02:08Z.
  - Um *Rolling build* contínuo.
- **[medido]** O bytecode confirma o README: o `tlc2/TLC.class` da 1.7.4 tem versão de classe 52
  (Java 8) e o da 1.8.0 tem versão 55 (Java 11). SHA-256 dos jars baixados:
  - 1.7.4: `936a262061c914694dfd669a543be24573c45d5aa0ff20a8b96b23d01e050e88`
  - 1.8.0: `67f9575c3b9ef7a0787b1bded34812862ffe79d711298e5a75b1a77720b19928`
- **[fonte]** O Homebrew não tem fórmula de linha de comando para o TLC. Só tem a cask
  `tla+-toolbox` 1.7.4, a IDE inteira, com uns 246 MB no zip da release. Para CLI e agente, o
  caminho é o jar.
- **[fonte]** A JVM limita o heap a 25% da RAM por padrão (`MaxRAMPercentage = 25`, lido com
  `java -XX:+PrintFlagsFinal`). Nesta máquina isso dá 6 GB. Numa máquina de 8 GB dá 2 GB, e o
  modelo 3x3 da seção 2 já precisou de 2,4 GB de RSS.
- **[fonte]** Na linha de comando o TLC usa 1 worker por padrão; `-workers auto` usa um por núcleo
  ([learntla, Optimizing](https://learntla.com/topics/optimization.html)). O TLC também avisa para
  rodar com `-XX:+UseParallelGC`.

**Na máquina do dev (macOS):** Java pelo Homebrew (`brew install openjdk@25`) ou Temurin. Esta
máquina já tinha o 25 e o 17. O jar fica fixado por versão e SHA-256, baixado uma vez para um
cache da máquina.

**No CI local:** o mesmo da ADR 0021 para o Dart. O motor usa o `java` do `PATH`, e ferramenta
ausente reprova com saída 127 (falha fechada). O requisito mora no documento da receita, não nos
requisitos de instalação do método. O jar entra como o `cargo-machete` e o `jscpd` entram hoje
(pesquisa de 2026-11-04, proposta 8): versão fixa, baixada uma vez, fora do caminho quente
**[inferido]**.

### Apalache

- **[fonte]** "We recommend running Apalache on Java 25 [...] should run on Java 21 or newer"
  ([installation/jvm.md](https://github.com/apalache-mc/apalache/blob/main/docs/src/apalache/installation/jvm.md)).
- **[fonte]** "We recommend to allocate at least 4GB of memory for the tool". A memória depende do
  solver SMT, o Z3 por padrão
  ([installation/index.md](https://github.com/apalache-mc/apalache/blob/main/docs/src/apalache/installation/index.md)).
- **[fonte]** A release v0.63.0 (2026-11-10) tem 192 MB em `.tgz`. Há também imagem Docker
  (`ghcr.io/apalache-mc/apalache`), que a própria doc desaconselha "unless you have a pressing need".
- **[fonte]** É um checador **limitado**: verifica até `--max-steps` passos (10 por padrão) e prova
  a invariante só até esse limite. Em troca, aguenta domínios numéricos grandes que o TLC não
  enumera ([Quint, Model Checkers](https://github.com/informalsystems/quint/blob/main/docs/content/docs/model-checkers.mdx)).

### Quint

- **[fonte]** Pacote npm `@informalsystems/quint` 0.34.0 (2026-11-22), `engines: node >= 18`. O
  Homebrew tem `quint` 0.33.1, que depende de `node`. Instalação oficial: `npm i
  @informalsystems/quint -g` ou `brew install quint`
  ([getting-started](https://github.com/informalsystems/quint/blob/main/docs/content/docs/getting-started.mdx)).
- **[fonte]** "The model checker requires Java Development Kit >= 21" (mesma página). O `quint
  verify` baixa o Apalache sozinho. Com `--backend=tlc`, o Quint traduz para TLA+ via Apalache e roda
  o TLC, então continua precisando do Apalache e do Java 21 ou mais novo (`quint verify --help`;
  model-checkers.mdx).
- **[medido]** `npm install` local em 2,5 s, com 41 MB de `node_modules`. Na primeira execução o
  Quint gravou **fora do projeto**, em `~/.quint`: o `rust-evaluator-v0.8.0` (2,4 MB, usado pelo
  `quint run`) e o `apalache-dist-0.62.4` (193 MB, usado pelo `quint verify`). Removi a pasta depois
  da medição.
- **[medido]** O `quint verify` sobe um servidor do Apalache na porta 8822 durante a checagem. Depois
  das checagens não havia processo nem porta abertos.

### Comparação para a casa

| | TLC (jar) | Apalache | Quint |
|---|---|---|---|
| Runtime | Java 11+ | Java 21+ | Node 18+ (`run`); Node e Java 21+ (`verify`) |
| Tamanho | 4,5 MB | 192 MB | 41 MB, mais 193 MB baixados em `~/.quint` |
| Garante | Todos os estados, de qualquer comprimento, dentro das constantes | Todos os caminhos até N passos | `run`: amostra aleatória (não prova); `verify`: o que o backend garante |
| Linguagem do modelo | TLA+ | TLA+ (com anotações de tipo) | Quint (sintaxe de programação, tipada) |

## 2. Tempo e explosão do espaço de estados

O modelo da seção 6 descreve um botão pago clicado `Cliques` vezes. Cada clique pode reenviar até
`MaxReenvios` vezes quando a resposta não chega. Cada tentativa roda num trabalhador próprio no
servidor, que consulta a chave e depois cobra e grava. A invariante: o pedido é cobrado no máximo
uma vez.

### Ver a checagem falhar

**[medido]** TLC 1.8.0, `-workers auto` (10), dois cliques, um reenvio:

| Variante | Resultado | Estados distintos | Tempo de parede |
|---|---|---|---|
| Sem chave de idempotência | **Viola** a invariante (saída 12) | 49 | 0,36 s |
| Com chave, mas consulta e gravação em dois passos | **Viola** a invariante, contraexemplo em 7 estados | 200 | 0,24 s |
| Com chave e gravação atômica (insert-if-absent) | Passa | 169 | 0,22 s |

O contraexemplo da corrida, em palavras: o cliente clica, a resposta não chega a tempo e ele reenvia.
As duas tentativas consultam a chave antes de qualquer uma gravar, e as duas cobram. Dá
`cobrancas = 2` com `chavesGravadas = {"pedido-1"}`. Esse é o bug que a chave de idempotência sozinha
não pega, e ele aparece já no menor limite possível (2 cliques, 1 reenvio).

### A escada de tamanhos (variante correta)

**[medido]**

| Cliques x reenvios | Estados gerados | Estados distintos | Profundidade | Parede, 10 workers | Parede, 1 worker | RSS máximo |
|---|---|---|---|---|---|---|
| 2 x 1 | 443 | 169 | 13 | 0,22 s | 0,40 s | 126 MB |
| 2 x 2 | 6.001 | 1.600 | 19 | 0,27 s | 0,38 s | 142 MB |
| 3 x 2 | 360.001 | 64.000 | 28 | 0,51 s | 1,00 s | 346 MB |
| 3 x 3 | 13.132.978 | 1.771.561 | 37 | 6,1 s | 23,8 s | 2,4 GB |
| 4 x 3 | (parei em 51,5 M distintos, aos 3 min) | ≈ 214 M (inferido) | — | ≈ 15 min (inferido) | — | 2,9 GB e 2,5 GB de disco quando parei |

**Onde explode:** as contagens são potências exatas. 1.600 = 40², 64.000 = 40³, 1.771.561 = 121³.
Cada clique é um ator independente, e os estados se multiplicam por ator: com 2 reenvios cada clique
contribui 40 combinações, com 3 contribui 121. Por isso 4 x 3 dá 121⁴ ≈ 214 M **[inferido]**. A
vazão medida com 10 workers foi de 15 a 18 M estados distintos por minuto, e o disco cresceu uns
2,5 GB a cada 50 M estados. Os dois juntos dão cerca de 15 min e mais de 10 GB **[inferido]**. A
explosão não vem da regra de negócio. Vem da **intercalação** de atores que não se coordenam: cada
reenvio e cada passo separado do servidor multiplica as ordens possíveis.

**O que segura a explosão:**

- **Constantes pequenas.** "Most bugs appear with small state spaces anyway, so there's not much
  benefit to using enormous constant inputs"
  ([learntla](https://learntla.com/topics/optimization.html)). **[medido]** Aqui os dois bugs
  aparecem em 2 x 1, com menos de 200 estados.
- **Conjuntos de simetria.** Quando os atores são intercambiáveis, a simetria corta o espaço por
  cerca do fatorial do tamanho do conjunto. No exemplo da learntla, caiu de 28 M para 4,7 M estados
  (mesma página). Exige que os cliques sejam *model values* e não números 1..N, e não combina com
  checagem de vivacidade.
- **Restrição de estado e `VIEW`.** Limitam a profundidade ou o que conta como estado diferente,
  mas "it's also really easy to remove valid states" (mesma página).
- **Simulação (`-simulate`) e Apalache limitado.** Trocam a garantia de cobrir todos os estados por
  alcance. No Specula, a busca em largura achou 187 dos 200 bugs que o model checking encontrou, e a
  simulação aleatória achou os outros 13. A mediana dos contraexemplos foi de 9 passos, e o p90 de 18
  ([Specula, §5.1](https://arxiv.org/abs/2607.25333)).

### Quint no mesmo modelo

**[medido]** Mesmo desenho escrito em Quint (seção 6):

| Comando | Variante | Resultado | Parede |
|---|---|---|---|
| `quint run` (simulador, 10.000 amostras) | corrida | Viola, achou em 10 ms | 0,23 s |
| `quint run` (10.000 amostras) | correta 2 x 1 | Nenhuma violação na amostra | 1,38 s (1.ª vez, com download do avaliador) |
| `quint run` (10.000 amostras) | correta 3 x 3 | Nenhuma violação na amostra | 0,46 s |
| `quint verify --backend=tlc` | correta 2 x 1 | Passa, 169 estados distintos (igual ao `.tla`) | 11,7 s (1.ª vez, com download do Apalache); 2,9 s depois |
| `quint verify --backend=tlc` | corrida | Viola | 2,9 s |
| `quint verify` (Apalache, 10 passos) | corrida | Viola | 4,0 s |
| `quint verify` (Apalache, 10 passos) | correta 2 x 1 | Passa até 10 passos | 12,1 s |

O `quint run` é amostragem: "nenhuma violação" ali não prova nada. A tradução para o TLC deu as
mesmas 169 contagens do `.tla` escrito à mão, então os dois modelos são o mesmo. O caminho do Quint
custa de 3 a 12 s por checagem, contra menos de 0,5 s do TLC direto, e traz Node, Java 21 ou mais
novo e 193 MB a mais.

## 3. Custo de tokens para o agente escrever e manter o modelo

**Não achei relato público com tokens por modelo do tamanho do nosso** (uma invariante, dezenas de
linhas). Nem o vídeo de origem (`transcricao_bQCBfcZZj0Y.md`) dá número: diz só "It's in beta, it
uses tokens, TLA plus needs Java, and it does one rule at a time". As fontes com número medem
sistemas inteiros:

- **[fonte] Specula** (Cheng et al., arXiv 2607.25333, v2 de 2026-08-03): Claude Code v2.1.97 com
  Opus 4.8, contexto de 1M e raciocínio máximo, em 48 projetos abertos.
  - Custo e tempo: "Specula takes 1.43–9.86 hours to check each system end-to-end, with a median of
    3.69 hours; these end-to-end checks cost $19–$168 US dollars of token consumption, with a median
    of $57" (§5.3).
  - **A Tabela 5 tem a linha de base mais próxima do que a casa faria.** É o Agent-TLA+, definido
    como "Claude Code equipped with the TLA+ Skills and MCPs":

    | Sistema | Agent-Raw | Agent-TLA+ | Specula |
    |---|---|---|---|
    | Autobahn | 27 min, US$ 5,99 | 69 min, US$ 16,46 | 110 min, US$ 28,96 |
    | CometBFT | 40 min, US$ 6,27 | 13 min, US$ 2,58 | 402 min, US$ 167,83 |
    | libspdm | 14 min, US$ 3,81 | 16 min, US$ 5,08 | 151 min, US$ 40,75 |
    | MongoDB | 15 min, US$ 3,82 | 15 min, US$ 4,26 | 157 min, US$ 47,54 |
    | sofa-jraft | 11 min, US$ 2,19 | 24 min, US$ 4,91 | 199 min, US$ 81,06 |

  - Qualidade, que pesa contra o caminho barato: o Agent-Raw e o Agent-TLA+ acharam 2 e 3 bugs,
    contra 62 do Specula. Deram 5 e 2 falsos positivos, e o Specula nenhum. Os autores concluem que
    "the official TLA+ tools bring no real improvement overall: what is lacking is not TLA+
    knowledge but the runtime feedback that helps the agents to repair and revise the models"
    (§5.2).
- **[fonte] SysMoBench** (arXiv 2509.23130, ICLR 2026): não mede custo. Mede qualidade, com até 3
  rodadas de correção via SANY e TLC e o melhor de 5 tentativas. Os modelos de referência têm de 75 a
  508 linhas de TLA+ (mediana de 219). Num spinlock, o Claude Sonnet 4 acertou 100% em sintaxe,
  execução, conformidade e invariante. No Raft do Etcd, acertou 25% em execução e 7,7% em
  conformidade.
- **[fonte] Avaliação da Loyola** (ai4fm, ICSOFT 2026): 30 LLMs e 205 especificações, com melhor
  correção semântica de só 8,6%
  ([ai4fm](https://ai4fm.cs.luc.edu/posts/llm-tla-evaluation-2025/)). Mede geração de linguagem
  natural para TLA+ sem laço com o TLC, então é o piso.

**Conversão para a ADR 0017 [inferido]:** a ADR mede em tokens equivalentes de entrada. Ao preço do
Opus 4.8 (US$ 5 por milhão de tokens de entrada, tabela de preços da Anthropic), US$ 1 equivale a
200 mil tokens.

- Agent-TLA+: de US$ 2,58 a US$ 16,46, ou seja, de **0,5 M a 3,3 M** por sistema.
- Specula: mediana de US$ 57, ou seja, **11,4 M**.
- O orçamento padrão da ADR 0017 é de 3 M por issue.

Um modelo de uma invariante sobre um fluxo de checkout é bem menor que um sistema distribuído
inteiro. O modelo desta pesquisa tem uns 90 linhas e foi escrito, rodado e corrigido em poucas
iterações. A estimativa razoável para escrevê-lo, vê-lo falhar e passar fica **perto do piso do
Agent-TLA+, uns 0,5 M a 1 M**. Isso é inferência sem medição. O piloto obrigatório do mapa #69 deve
medir com `rodar custo`.

**Manutenção:** nenhuma fonte mede o custo de manter. A skill `maintain-formal-verification-skill`
do pstack descreve o trabalho: rodar a checagem como está, ler o diff do código coberto desde o
commit sincronizado, decidir se o modelo ainda descreve o código e repetir o contraexemplo no código
real ([SKILL.md](https://github.com/cursor/plugins/blob/main/harness/pstack/claude-code/skills/maintain-formal-verification-skill/SKILL.md)).
O custo cresce com o tamanho do diff coberto, não com o modelo **[inferido]**. O caso barato é a
checagem passar e o diff não tocar o estado guardado. O caso caro é o contraexemplo, que exige
repeti-lo passo a passo no código.

## 4. Cabe no pre-push?

**[fonte]** O `rodar ci` (ADR 0015) roda em sequência as regras `comando` de
`docs/regras-de-codigo.json`. Uma regra `comando` com `{arquivos}` no `executar` só roda quando há
arquivo alterado que case com o glob `arquivos`; com a lista vazia, a regra é pulada
(`validador.rs`, ramo `"comando"`). O `pre-push` chama o `rodar ci`.

**[medido]** Nos limites que pegam os dois bugs (2 x 1 e 2 x 2), o TLC leva menos de 0,5 s de parede
com 1 worker e 130 a 140 MB de RSS, menos que um `claude -p` da revisão por modelo (219 MiB,
pesquisa de 2026-11-04). Em 3 x 2 ainda é 1 s. A partir de 3 x 3 passa de 20 s com 1 worker e de 2 GB
de memória, o que não cabe no pre-push numa máquina de 8 GB.

**Conclusão [inferido]:**

- **Pre-push:** cada modelo tem um `.cfg` pequeno (o menor limite que já pega o bug que motivou a
  invariante), rodado com `-workers 1 -XX:+UseParallelGC -Xmx512m` e um prazo curto. Entra como
  regra `comando` com `arquivos` cobrindo o `.tla`, o `.cfg` e o código coberto, para pular quando
  nada disso mudou. Ausência de `java` reprova (ADR 0021).
- **Sob demanda:** um `.cfg` maior para quando o modelo muda de verdade, rodado pelo agente
  dentro da trava pesada da máquina (ADR 0016), com o resultado na Evidence da PR. Escrever e manter
  o modelo (os tokens) é sempre sob demanda: na issue que toca o risco `RK`, nunca no hook.
- **Ferramenta:** TLC direto pelo jar fixado. Exige só Java 11 ou mais novo, roda em menos de
  0,5 s e não baixa nada para fora do projeto. O Quint fica como opção de leitura (sintaxe mais
  próxima de TS), não de CI: o `verify` traz Node, Java 21 ou mais novo, 193 MB e de 3 a 12 s. O
  Apalache só entra se um risco precisar de domínio numérico grande.

## 5. O que fica em aberto

- O custo real de tokens de um modelo pequeno na casa: medir no piloto com `rodar custo`.
- A v1.8.0 do TLC saiu como *Pre-release* no próprio dia desta pesquisa. A *Latest* estável é a
  1.7.4 (2024), que roda em Java 8. A receita precisa escolher qual fixar.
- A simetria e o `VIEW` não foram medidos neste modelo, porque usam *model values* em vez de 1..N.
- Não medi numa máquina de 8 GB. Os números de memória da escada valem como piso.

## 6. Como reproduzir

Tudo no scratchpad da sessão, sem instalação global. Java 25 já estava na máquina.

```sh
gh release download v1.8.0 -R tlaplus/tlaplus -p tla2tools.jar -O tla2tools-1.8.0.jar
java -XX:+UseParallelGC -jar tla2tools-1.8.0.jar -deadlock -workers 1 \
  -metadir meta/corrida_2x1 -config corrida_2x1.cfg Checkout.tla
npm install @informalsystems/quint   # local, 0.34.0
npx quint run --main=corrida --invariant=cobradoNoMaximoUmaVez --max-samples=10000 --max-steps=20 checkout.qnt
npx quint verify --backend=tlc --main=correto --invariant=cobradoNoMaximoUmaVez checkout.qnt
```

`-deadlock` desliga a checagem de deadlock, porque o modelo para de propósito quando todo clique foi
respondido. Cada `.cfg` só troca as constantes, por exemplo `corrida_2x1.cfg`:

```
SPECIFICATION Spec
CONSTANTS
    Cliques = 2
    MaxReenvios = 1
    UsaChave = TRUE
    Atomico = FALSE
INVARIANT CobradoNoMaximoUmaVez
```

### `Checkout.tla`

```tla
---------------------------- MODULE Checkout ----------------------------
(* Checkout com botão pago clicado mais de uma vez, retry do cliente e      *)
(* chave de idempotência no servidor.                                       *)
(* Cada clique vira uma ou mais tentativas (a resposta pode se perder, e o   *)
(* cliente reenvia). O servidor trata cada tentativa num trabalhador próprio,*)
(* em paralelo, em dois passos: consulta a chave e depois cobra e grava.     *)
EXTENDS Naturals, FiniteSets

CONSTANTS
    Cliques,        \* quantos cliques no botão pago (2 = clique duplo)
    MaxReenvios,    \* quantos reenvios cada clique pode fazer
    UsaChave,       \* TRUE: todas as tentativas do pedido levam a mesma chave
    Atomico         \* TRUE: consultar e gravar a chave é um passo só

IdsCliques == 1..Cliques
Tentativas == IdsCliques \X (0..MaxReenvios)

\* A chave que cada tentativa leva ao servidor.
ChaveDa(tentativa) == IF UsaChave THEN "pedido-1" ELSE tentativa

VARIABLES
    enviadasPorClique,   \* quantas tentativas cada clique já enviou
    respondido,          \* o cliente daquele clique já recebeu resposta
    estadoTrabalhador,   \* estado de cada tentativa no servidor
    chavesGravadas,      \* chaves que o servidor já gravou
    cobrancas            \* quantas vezes o cartão foi cobrado

variaveis == <<enviadasPorClique, respondido, estadoTrabalhador, chavesGravadas, cobrancas>>

Init ==
    /\ enviadasPorClique = [clique \in IdsCliques |-> 0]
    /\ respondido = [clique \in IdsCliques |-> FALSE]
    /\ estadoTrabalhador = [tentativa \in Tentativas |-> "nao_enviada"]
    /\ chavesGravadas = {}
    /\ cobrancas = 0

\* O cliente envia (primeira vez) ou reenvia (a resposta não chegou a tempo).
Enviar(clique) ==
    /\ ~respondido[clique]
    /\ enviadasPorClique[clique] <= MaxReenvios
    /\ LET tentativa == <<clique, enviadasPorClique[clique]>> IN
        estadoTrabalhador' = [estadoTrabalhador EXCEPT ![tentativa] = "recebida"]
    /\ enviadasPorClique' = [enviadasPorClique EXCEPT ![clique] = @ + 1]
    /\ UNCHANGED <<respondido, chavesGravadas, cobrancas>>

\* Passo 1 do servidor: consulta a chave. Se for atômico, já cobra e grava.
Consultar(tentativa) ==
    /\ estadoTrabalhador[tentativa] = "recebida"
    /\ IF ChaveDa(tentativa) \in chavesGravadas
         THEN /\ estadoTrabalhador' = [estadoTrabalhador EXCEPT ![tentativa] = "respondida"]
              /\ UNCHANGED <<chavesGravadas, cobrancas>>
         ELSE IF Atomico
           THEN /\ estadoTrabalhador' = [estadoTrabalhador EXCEPT ![tentativa] = "respondida"]
                /\ chavesGravadas' = chavesGravadas \cup {ChaveDa(tentativa)}
                /\ cobrancas' = cobrancas + 1
           ELSE /\ estadoTrabalhador' = [estadoTrabalhador EXCEPT ![tentativa] = "consultada"]
                /\ UNCHANGED <<chavesGravadas, cobrancas>>
    /\ UNCHANGED <<enviadasPorClique, respondido>>

\* Passo 2 do servidor (só no caminho não atômico): cobra e grava a chave.
CobrarEGravar(tentativa) ==
    /\ estadoTrabalhador[tentativa] = "consultada"
    /\ estadoTrabalhador' = [estadoTrabalhador EXCEPT ![tentativa] = "respondida"]
    /\ chavesGravadas' = chavesGravadas \cup {ChaveDa(tentativa)}
    /\ cobrancas' = cobrancas + 1
    /\ UNCHANGED <<enviadasPorClique, respondido>>

\* A resposta chega ao cliente. Se não chegar, o cliente pode reenviar.
Responder(tentativa) ==
    /\ estadoTrabalhador[tentativa] = "respondida"
    /\ estadoTrabalhador' = [estadoTrabalhador EXCEPT ![tentativa] = "entregue"]
    /\ respondido' = [respondido EXCEPT ![tentativa[1]] = TRUE]
    /\ UNCHANGED <<enviadasPorClique, chavesGravadas, cobrancas>>

Next ==
    \/ \E clique \in IdsCliques : Enviar(clique)
    \/ \E tentativa \in Tentativas :
         Consultar(tentativa) \/ CobrarEGravar(tentativa) \/ Responder(tentativa)

Spec == Init /\ [][Next]_variaveis

\* A invariante: o pedido é cobrado no máximo uma vez.
CobradoNoMaximoUmaVez == cobrancas <= 1
```
